## Dropbox API for an unattended sync of a 30,000-file shared folder

Dropbox API v2 fully supports an unattended weekly pull of the 32,600-file 'Trizetto Data' shared folder, provided the app is built as a Scoped, Full-Dropbox app authorized once with token_access_type=offline (long-lived refresh token; ~4 h access tokens minted from POST /oauth2/token) and read-only scopes (files.metadata.read, files.content.read, sharing.read, account_info.read). The shared folder is its own namespace (id <namespace id>) and should be addressed as 'ns:<namespace id>' (or via the Dropbox-API-Path-Root namespace_id header) rather than by display path. Enumerate once with /2/files/list_folder recursive=true limit=2000 (1..2000, approximate) and paginate with /2/files/list_folder/continue; then persist the cursor and call /continue weekly to receive only adds/edits/deletes (renames appear as DeletedMetadata + new FileMetadata with the same id); handle 409 'reset' by re-listing. Backfill must be ~32,600 single /2/files/download calls (download_zip is capped at 10,000 entries / 20 GB; temporary links die in 4 h); weekly deltas are ~150 files. Dropbox publishes no numeric rate limits; 429s always carry Retry-After and the official Python SDK (dropbox 12.2.4, Oct 2026, Python >=3.11, must be >=12.0.2 since the Jan 2026 root-cert change) auto-refreshes tokens and retries 429/5xx, so no hand-rolled HTTP is needed. Webhooks (10-second response, HMAC-SHA256 signature, account-ids-only payload) are the recommended push trigger and can complement a weekly cron; longpoll is for client apps. Compliance is the sharpest finding: Dropbox signs BAAs only for Standard/Advanced/Enterprise/Education team plans (electronic signature in the Admin Console, US only, 'before you transfer PHI'), not for individual accounts, and Dropbox states that third-party/connected apps, which include ODA's own API app and the Claude Dropbox connector, are 'not covered by your Dropbox terms of use, including a BAA'. If the folder is mounted in a personal Dropbox today, there is no BAA covering the 835 PHI.

### [VERIFIED] An unattended job must use the OAuth 2 authorization-code flow with token_access_type=offline: Dropbox retired the creation of long-lived access tokens on September 30, 2021, so the job must store a refresh token (which 'won't expire automatically') and mint short-lived access tokens (sample expires_in 14400 s = 4 h) from POST https://api.dropboxapi.com/oauth2/token with grant_type=refresh_token.

**Checker's wording:** CONFIRMED, with refinements. As of 2026-11-06 the only Dropbox-supported way for an unattended server job to read a user's Dropbox content (including a mounted shared folder) is the OAuth 2 authorization-code flow requested with token_access_type=offline, after a ONE-TIME interactive consent by the Dropbox account owner; Dropbox's OAuth guide summary table says verbatim: "A server-side application that requires background access -> Use the OAuth code flow, with refresh tokens." Authorization URL: https://www.dropbox.com/oauth2/authorize?client_id=<APP_KEY>&response_type=code&token_access_type=offline[&redirect_uri=...][&scope=...][&state=...]; the reference states "If omitted, this parameter defaults to online", and with offline the /oauth2/token payload "will contain a short-lived access_token and a long-lived refresh_token that can be used to request a new short-lived access token as long as a user's approval remains valid." The refresh_token field is documented as "long-lived and won't expire automatically. It can be stored and re-used multiple times." Refresh: POST https://api.dropboxapi.com/oauth2/token (the documented URL structure; Dropbox's own curl examples use https://api.dropbox.com/oauth2/token and both hosts answer) with grant_type=refresh_token, refresh_token, client_id, client_secret (or HTTP Basic app_key:app_secret); response {access_token, expires_in, token_type:"bearer"} and "This request won't return a new refresh token since refresh tokens don't expire automatically and can be reused repeatedly" (no rotation). The 2022 post adds "Refresh tokens are app- and user-specific." Long-lived tokens: the 2020 migration post says "On September 30th, 2021, Dropbox will retire the creation of long-lived access tokens — resulting in all new tokens being short-lived" and carries the update "Dropbox is no longer offering the option to create new long-lived access tokens, so the Access token expiration drop-down is no longer available"; the OAuth guide says "In the past, the Dropbox API used only long-lived access tokens. These are now deprecated." The Developer Console "Generate access token" button yields a short-lived token for your own account only, with no refresh token, so it cannot power a weekly job. 401 handling: AuthError variants are invalid_access_token ("revoked by Dropbox or the user... you should re-authenticate the user"), expired_access_token ("The access token has expired"), user_suspended, missing_scope, route_access_denied; the error guide says "With the exception of suspension, retrying a 401 will not succeed." Revocation: the user via Settings > Apps > Disconnect, a team admin via the Team apps page, or the app via /2/auth/token/revoke, which "disables that refresh token, as well as any other access tokens for that refresh token" (never call it from the job). PKCE (code_challenge_method S256 recommended or plain; code_verifier 43-128 chars) is "the recommended flow for client-side apps" but is also allowed for server apps, and then the refresh call needs only client_id (no client_secret). REFINEMENTS the original omits: (1) expires_in is documented only as "the length of time in seconds that the access token will be valid for" — samples show 14400 (reference) and 14399 (2020 post) and the guide says only "generally long enough for a reasonable web session" — so always honor expires_in rather than hard-coding 4 h (the official Python SDK does this: Dropbox(oauth2_refresh_token=..., app_key=..., app_secret=...) auto-refreshes; app_secret is optional if PKCE was used). (2) The token reference now documents an optional refresh_token_expiration_seconds parameter (authorization_code exchange only); "If this parameter is omitted, the refresh token will be valid indefinitely, until revoked" — an unattended job must omit it. (3) A grant_type=client_credentials "app auth token" exists today but has no user context and "can only be used to call endpoints that use App Authentication" (e.g. listing/downloading via a shared link), so it is not an alternative for reading the owner's folder short of publishing a public link to PHI, which also supports only non-recursive listing. (4) The implicit response_type=token flow is marked Legacy and never returns a refresh token; the Python SDK still exposes token_access_type='legacy' in its enum, but Dropbox no longer issues long-lived tokens for new apps. (5) The redirect_uri must be registered and HTTPS (localhost excepted); if omitted "the code will be presented directly to the user and they will be invited to enter the information in your app", which suits a one-time bootstrap script. If scope is omitted "the authorization page will request all scopes selected on the Permissions tab"; adding scopes later requires a new consent. A new app starts in Development status and "will only be authorized for you", which is sufficient for a single-owner job. (6) Operationally: treat expired_access_token as "refresh", treat invalid_access_token/revocation as "page a human to re-consent", and treat the stored refresh token as a long-lived PHI-access credential (secret storage, rotate by re-consenting then revoking the old token).

### [VERIFIED] The app must be created with 'Full Dropbox' access, not 'App folder': an App-folder app is rooted to /Apps/<app name> and cannot see a shared folder mounted elsewhere in the owner's Dropbox. A single-owner internal tool can stay in 'development' status indefinitely with no Dropbox production review.

**Checker's wording:** The Dropbox app for the weekly sync must be created with "Full Dropbox" access, not "App folder". Per Dropbox's current docs, an App-folder app's API calls are rooted to its dedicated folder under /Apps/<app folder name> (the folder name defaults to the app name and can be changed in the console), "paths outside of this location are not accessible", the Dropbox-API-Path-Root header can only re-root "according to the authorized permissions of the access token", and the app "gets read and write access to this folder only". So an App-folder token cannot reach the "Trizetto Data" shared folder mounted elsewhere in the owner's Dropbox, and the obvious workaround does not exist: Dropbox's Help Center states app folders "are incompatible with shared folders or team folders" and you get an error if you try to "Add a shared folder to an app folder", share an app folder, or add an app folder to a shared folder (the share_folder API likewise returns is_app_folder / inside_app_folder / contains_app_folder errors and "does not support apps with the app folder permission"). Full Dropbox access, which Dropbox describes as appropriate "when your application needs to regularly access pre-existing content in the user's account", is therefore required; note the access type cannot be changed later (you must delete the app and create a new one). On status: every new app is created in development status, initially authorized only for the creator's own account; it "functions the same as any production status app" except it can link at most 500 users after "Enable additional users", and the only trigger for a mandatory production review (and a freeze on linking additional users) is linking 50 users within a two-week window. Dropbox explicitly says "Many apps such as those for demos, hackathons, staging environments, and internal tools can stay in development status", a production request "will not be reviewed until your app has linked with at least 50 Dropbox users", and neither the docs nor the Developer Terms (effective March 1, 2025) impose any time limit or inactivity rule on development-status apps. A single-owner internal tool can therefore remain in development status with no Dropbox production review (the docs do not use the word "indefinitely", but state no expiry).

Path-root modes doc: 'For App Folder apps, calls are rooted to the app folder. For Full Dropbox apps, calls are rooted to the user's Dropbox folder by default.' OAuth guide: App Folder permissions apply 'within its app folder only (in the /apps folder)'; Full Dropbox applies to 'all data within the user's Dropbox account'. Developer guide: 'A dedicated folder named after your app is created within the Apps folder of a user's Dropbox'; app creation 'walks you through three steps: choose an API, choose the type of access you need, and name your app'; 'For non-Business API apps this can be either App folder or Full Dropbox.' ## How underpayment analytics are done: commercial tools, ModMed EMA, TriZetto

Research lens: how underpayment/downcoding analytics are done commercially, what ModMed EMA exposes, and how TriZetto delivers data. Key results: (1) The X12 835 standard requires the originally submitted code in SVC06 whenever the adjudicated code in SVC01 differs (X12 RFI 2320/2375), so SVC06≠SVC01 is the primary downcode/bundling signal; payers that omit it are non-compliant, which is why a fallback comparison of EMA billed code vs 835 paid code is required. (2) Every commercial underpayment tool (Rivet, MD Clarity RevFind, Adonis, Experian Contract Manager, Waystar, TriZetto ARM, athenaNet, AdvancedMD) is anchored on loaded contracts/fee schedules; none documents a contract-free mode, and athenaNet literally shows 'unknown' without allowables. ODA has no contracts loaded, so the build must derive expected allowed amounts statistically; the only regulatory precedent for that is CMS's hospital price transparency method (median/10th/90th percentile of 835 allowed amounts, 12–15 month lookback, next-highest-observed rule, unit normalization). (3) The Medicare fee schedule is a legal floor only for non-contract MA providers (42 CFR 422.214); for ODA's contracted Humana/UHC MA lines it is a benchmark, not a right. (4) 2025 payer E/M downcoding programs are documented in primary sources: Cigna R49 (effective 10/1/2025, 99204-5/99214-5/99244-5, one level, records restore original level, bypass at >=5 claims and 80%), Aetna CCRP (commercial only per APMA, RARC N22 on the ERA, never below level 3, removal after overturning a threshold in 5–6 months), plus AASM's list of 13 payers including Humana, UHC and Anthem. No published downcoding prevalence rate exists. (5) ModMed's March-2026 EHI bulk data dictionary reveals PM tables that carry CARC/RARC per bill item (payer_adjustments_detail), ERA receipts (era_received), provider-level (PLB) adjustments, claim logs with PENDING_APPEAL status, denial categories, and original-vs-final bill procedures; bill_item_id is the natural join key, but whether it is transmitted as REF*6R is unconfirmed. ModMed's API has ChargeItem/Account but no claim/remittance resource and requires vendor onboarding, so Dropbox xlsx exports remain the only ERA path from EMA. (6) TriZetto delivers 835s as .RMT files via support-enabled SFTP/portal 'Remits' folder, generated roughly every 3–4 hours, with configurable file names (check number/amount/date/payer); no public API or 837-history export is documented. (7) CAQH CORE 360's four business scenarios, X12 CARC/RARC/PLB definitions, and HFMA's denial KPI formulas give a defensible taxonomy and metric set for the dashboard.

### [UNVERIFIED] The only published, regulator-sanctioned method for deriving an 'expected allowed amount' from 835 data is CMS's hospital price-transparency rule: median, 10th and 90th percentile of historical 835 allowed amounts with a 12–15 month lookback, a 'next highest observed value' rule for percentiles, per-unit normalization, and exclusion of zero-dollar claims from counts.

CMS Hospital Price Transparency FAQ: 'Hospitals must use electronic data interchange (EDI) 835 electronic remittance advice (ERA) or an equivalent source of remittance data to calculate and encode the 10th, median, and 90th percentile allowed amounts as well as the count of allowed amounts'; 'Should the calculated amount ... fall between two observed allowed amounts, hospitals are instructed to use the next highest observed value'; 'a lookback period of no less than 12 months and no longer than 15 months'; for unit-based lines 'divide the total allowed amount ... by the number of units' and treat the unit amount 'as being a repeated observation'; per the CY2026 OPPS rule 'hospitals should exclude the zero-dollar claims from the count of allowed amount calculations'. 45 CFR 180.20 defines 'Median allowed amount means the median of the total allowed amounts the hospital has historically received' with the same next-highest-observed rule. No white paper validating median-based inference against actual contracts was found (search budget was exhausted before a dedicated methods search). ODA's observed data supports the approach: BCBS 99213 $51.00 and 99214 $63.89 'flat across 2024 to 2026', while Medicare KY 99213 ranges $70.81–$83.30 (locality/year/sequestration/G2211 effects), so a per-year, per-payer mode will be sharp for commercial payers and needs year/locality stratification for Medicare.

**What it means for ODA:** Baseline algorithm for ODA: key = (payer_id normalized, CPT, sorted pricing modifiers, units-normalized, calendar year, primary/secondary flag); include only lines with AMT*B6 > 0 and CLP02 in {1,2,3} with primary adjudication; compute mode and median with next-highest-observed rule, p10/p90, and count; minimum support rule (e.g., n>=8 lines and >=3 distinct claims) before a key is 'established', otherwise fall back to prior year scaled by the payer's observed year-over-year ratio, then to Medicare PFS. ### [UNVERIFIED] Medicare Advantage: a non-contracted provider must accept the original Medicare amount as payment in full (42 CFR 422.214(a)), which acts as a payment floor that MA plans may reduce by the 2% sequestration; contracted-provider payment is purely contractual and typically expressed as a percentage of Medicare, and ODA's own data shows exact multipliers: Humana MA 99213 $66.64 = 80.00% and UHC MA $76.64 = 92.00% of the KY 2025 MPFS $83.30.
